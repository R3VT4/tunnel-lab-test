# Tunnel Lab — نسخهٔ ۰٫۴ آزمایشی برای تست نصب

این نام موقت است؛ انتخاب نام نهایی به بعد موکول شده است.
هدف فعلی: پایهٔ قابل‌آزمایش انتقال TCP و دیتاگرام UDP بین دو سرور لینوکسی،
با TLS 1.3 و تأیید هویت دوطرفه، کنترل از ترمینال و صفحهٔ وب وضعیت واقعی.

این نسخه ادعای سرعت بالاتر از ابزارهای دیگر ندارد. آزمون محلی با اندازه‌گیری
پهنای باند در مسیر واقعی ایران/خارج تفاوت دارد.

برای نصب و آماده‌سازی GitHub، ابتدا [INSTALL_FA.md](INSTALL_FA.md) را بخوان.
اگر فقط می‌خواهی فایل اجرایی را بررسی کنی: `./bin/tunnellab-linux-amd64 selftest`.

## چه چیزی کار می‌کند؟

- حالت مستقیم TCP: برنامه → edge → ارتباط TLS → relay → سرویس مقصد.
- حالت مستقیم UDP-over-TLS: مرز دیتاگرام‌ها حفظ می‌شود؛ کانال بین سرورها TCP/TLS است.
- دستور probe: سنجش احراز‌شدهٔ زمان اتصال، تأخیر و انتقال داده تا سرور مقابل.
- حالت معکوس: reverse-relay اتصال کنترل و اتصال‌های داده را به reverse-edge آغاز می‌کند.
- اتصال مجدد کانال کنترل با فاصلهٔ افزایشی و اندکی تأخیر تصادفی؛ ضربان دوره‌ای برای تشخیص قطع کانال.
- قطع کانال کنترل به‌تنهایی اتصال‌های دادهٔ برقرارشده را قطع نمی‌کند؛ خرابی خود مسیر داده همچنان انتقال را پایان می‌دهد.
- شناسهٔ دادهٔ یک‌بارمصرف و وابسته به گواهی نشست کنترل؛ کنترل تکراری هم‌زمان پذیرفته نمی‌شود.
- هر اتصال ورودی، یک اتصال مستقل تا relay دارد؛ جریان‌ها روی یک TCP مشترک جمع نمی‌شوند.
- مقصد relay ثابت و از فایل تنظیمات تعیین می‌شود.
- گواهی سرور، گواهی کلاینت و نام سرور بررسی می‌شوند؛ گزینهٔ غیرفعال‌کردن بررسی گواهی نداریم.
- سقف اتصال هم‌زمان، مهلت راه‌اندازی اتصال و مهلت بی‌فعالیتی.
- پشتیبانی از بستن یک‌طرفهٔ TCP؛ مقصد می‌تواند پس از پایان درخواست، پاسخ را برگرداند.
- صفحهٔ وب محلی و دستور ترمینالی وضعیت، متصل به شمارنده‌های همان پردازش.
- خاموش‌شدن با SIGINT یا SIGTERM، همراه با بستن اتصال‌های فعال.
- نصب سرویس systemd با کاربر اختصاصی؛ مدیریت چند نمونه از ترمینال و بررسی تداخل پورت.
- دستور selftest داخل فایل اجرایی، بدون نیاز به Go، Python یا سرور خارجی.
- فایل ساخت انتشار GitHub برای Linux amd64 و arm64، همراه با checksum.

## چه چیزی هنوز وجود ندارد؟

UDP بومی بین سرورها، UDP معکوس، QUIC، رابط TUN، انتخاب مسیر، تجمیع پهنای باند، بازیابی نشست،
پنل مدیریت راه دور، تغییر تنظیمات از وب، چرخش/ابطال گواهی و ارتقای خودکار.
قطع اتصال فعال باعث پایان آن می‌شود؛ اتصال‌های جدید تلاش تازه می‌کنند.
TLS بین edge و relay برقرار است؛ بخش برنامه تا edge و relay تا مقصد، TCP عادی است،
مگر اینکه خود سرویس از رمزگذاری استفاده کند.

## اجرای محلی، قدم‌به‌قدم

اگر فایل اجرایی Linux amd64 همراه بسته است، در همان پوشه اجرا کن:

```bash
chmod +x bin/tunnellab-linux-amd64
./bin/tunnellab-linux-amd64 version
```

یا با Go 1.26 به‌روز بساز:

```bash
go test -race ./...
go build -buildvcs=false -o bin/tunnellab-linux-amd64 .
```

پوشهٔ تنظیمات آزمایشی را فقط یک بار بساز. دستور init روی پوشهٔ موجود چیزی نمی‌نویسد:

```bash
./bin/tunnellab-linux-amd64 init -dir demo
```

در ترمینال اول یک سرویس آزمایشی محلی اجرا کن؛ Python 3 لازم است:

```bash
python3 -m http.server 9000 --bind 127.0.0.1
```

در ترمینال دوم:

```bash
./bin/tunnellab-linux-amd64 run -config demo/relay.json
```

در ترمینال سوم:

```bash
./bin/tunnellab-linux-amd64 run -config demo/edge.json
```

در ترمینال چهارم:

```bash
curl --fail http://127.0.0.1:8080/
./bin/tunnellab-linux-amd64 status -url http://127.0.0.1:9081
```

آدرس صفحهٔ وضعیت edge: http://127.0.0.1:9081

آدرس صفحهٔ وضعیت relay: http://127.0.0.1:9082

در این مرحله بازشدن صفحهٔ تست در 8080 یعنی داده از دو پردازش و ارتباط TLS عبور کرده است.

## آزمایش خودکار بدون داشتن سرور

با Python 3 و فایل اجرایی لینوکس:

```bash
python3 scripts/smoke.py
python3 scripts/smoke.py --reverse
python3 scripts/udp_smoke.py
python3 scripts/install_smoke.py
```

هر دستور یک مقصد HTTP، دو پردازش تونل، گواهی موقت و پورت‌های محلی جدا می‌سازد؛
پاسخ را دقیق مقایسه می‌کند و پردازش‌ها را پس از تست می‌بندد. هیچ سرور خارجی لازم نیست.
آزمون‌های Go علاوه بر این، قطع کنترل هنگام انتقال فعال، برگشت اتصال و شناسهٔ تکراری را می‌سنجند.

## اجرای دستی حالت معکوس

از پوشهٔ demo تازه‌ساخته‌شده با همین نسخه استفاده کن. گواهی‌های init نسخهٔ ۰٫۱
برای حالت معکوس کافی نیستند؛ روی یک پوشهٔ تازه init اجرا کن و تنظیمات هر دو طرف را با هم به‌روز کن.
دو حالت مستقیم و معکوسِ نمونه از پورت ورودی یکسان استفاده می‌کنند؛ هم‌زمان اجرا نکن.
سرویس نمونه روی 9000 را مثل بخش قبل اجرا کن، سپس در دو ترمینال:

```bash
./bin/tunnellab-linux-amd64 run -config demo/reverse-edge.json
./bin/tunnellab-linux-amd64 run -config demo/reverse-relay.json
```

در ترمینال سوم:

```bash
curl --fail http://127.0.0.1:8080/
```

در حالت معکوس، `reverse-edge` دو پورت دارد: `listen` برای ترافیک مصرف‌کننده و
`tunnel_listen` برای اتصال‌های احرازشدهٔ reverse-relay. سمت سرویس هیچ listener مربوط به تونل ندارد.
برای دو سرور واقعی، `tunnel_listen` را روی رابط مناسب سمت ورودی قرار بده و `peer` سمت سرویس
را برابر آدرس همان پورت بگذار. `target` فقط در سمت سرویس تنظیم می‌شود.
نام بررسی گواهی در reverse-relay برابر `edge.tunnellab.local` است.
فایل‌های هر نقش همان edge.crt/edge.key و relay.crt/relay.key هستند؛ فایل JSON متناظر با reverse را کپی کن.

اگر کنترل در دسترس نباشد، ورودی‌های جدید سریع بسته می‌شوند. در زمان راه‌اندازی اتصال،
حداکثر ده ثانیه انتظار وجود دارد. اگر مقصد خطا بدهد یا relay ظرفیت نداشته باشد،
درخواست جدید ممکن است تا همین مهلت منتظر بماند؛ صف نامحدود ایجاد نمی‌شود.
هر درخواست داده یک اتصال TLS جدا دارد؛ این نسخه هنوز pooling یا multiplexing داده ندارد.

## انتقال به دو سرور واقعی

ابتدا تست محلی را کامل کن. جغرافیای سرورها در قالب تنظیمات نقشی ندارد؛ مسیر شبکه مهم است.
در نمونهٔ زیر A ورودی ترافیک و B میزبان سرویس مقصد است.

۱. یک بار init را روی دستگاه امن اجرا کن. فقط یک مجموعهٔ مشترک بساز؛ اجرای مستقل init
روی هر سرور دو گروه اعتماد متفاوت تولید می‌کند که به هم اعتماد ندارند.

۲. این چهار فایل را با SCP/SFTP به A منتقل کن:

- `edge.json`
- `edge.crt`
- `edge.key`
- `ca.crt`

۳. این چهار فایل را به B منتقل کن:

- `relay.json`
- `relay.crt`
- `relay.key`
- `ca.crt`

کلید خصوصی هر نقش را فقط در اختیار همان نقش نگه دار؛ مجوز پیشنهادی فایل کلید 0600 است.
نسخهٔ آزمایشی برای یک جفت سرور طراحی شده است. گواهی‌های برگ ۹۰ روز اعتبار دارند؛
کلید امضای CA روی دیسک ذخیره نمی‌شود. صدور هویت جدید و تمدید خودکار هنوز پیاده نشده‌اند.
راه آزمایشی تعویض: ساخت گروه تازه و تعویض هماهنگ فایل‌های هر دو طرف، با وقفه در سرویس.

۴. روی B در `relay.json`:

- `listen`: مثلاً `0.0.0.0:7443` برای دریافت اتصال تونل.
- `target`: آدرس واقعی سرویس، مثلاً `127.0.0.1:9000`.
- `admin`: همان `127.0.0.1:9082` بماند.

۵. روی A در `edge.json`:

- `peer`: آی‌پی یا دامنهٔ B به همراه پورت، مثلاً `203.0.113.20:7443`؛ این IP نمونه است.
- `listen`: مثلاً `127.0.0.1:8080` اگر سرویس فقط محلی مصرف می‌شود، یا آدرس رابط موردنیاز.
- `server_name`: همان `relay.tunnellab.local` بماند؛ این نام هویت گواهی است، نه نیاز به DNS عمومی.
- `admin`: همان `127.0.0.1:9081` بماند.

مسیر `ca`، `cert` و `key` نسبت به پوشهٔ فایل JSON تفسیر می‌شود.
فایروال B باید TCP پورت 7443 را از A بپذیرد. پورت ورودی A را فقط برای مصرف‌کنندگان موردنظر باز کن.
برنامه برای پورت‌های نمونه نیاز به root ندارد و تنظیمات فایروال/مسیریابی سیستم را تغییر نمی‌دهد.

برای دیدن صفحهٔ وضعیت سرور A روی کامپیوترت، یک اتصال SSH جدا برقرار کن:

```bash
ssh -N -L 9081:127.0.0.1:9081 USER@SERVER_A
```

سپس http://127.0.0.1:9081 را باز کن. صفحهٔ وب این نسخه فقط مشاهده‌ای است و از بیرون
روی پورت عمومی منتشر نمی‌شود. درخواست با Host غیرلوپ‌بک هم رد می‌شود؛ در مرورگر از 127.0.0.1 استفاده کن.

## معنی شمارنده‌ها

- `accepted`: اتصال‌های پذیرفته‌شده در سوکت؛ لزوماً احراز هویت نشده‌اند.
- `active`: اتصال‌های در حال راه‌اندازی یا انتقال.
- `rejected`: اتصال‌هایی که به دلیل سقف ظرفیت بسته شدند.
- `errors`: خطاهای راه‌اندازی یا انتقال؛ تشخیص جزئی علت‌ها برای مرحلهٔ بعد است.
- `completed`: انتقال‌هایی که هر دو جهتشان بدون خطای گزارش‌شده پایان یافته است.
- `forwarded_bytes`: بایت‌های دادهٔ برنامه که به سوکت خروجی نوشته شده‌اند.
- `returned_bytes`: بایت‌های دادهٔ برنامه که در جهت برگشت نوشته شده‌اند.
- `control_connected`: برقرار بودن کانال کنترل در حالت معکوس؛ نشانهٔ دسترسی مقصد نیست.
- `control_reconnects`: شمار تلاش‌های اتصال مجدد در reverse-relay، شامل تلاش پیش از اولین اتصال موفق.
- `pending`: درخواست‌های منتظر اتصال داده در reverse-edge؛ سقف آن از max_connections بیشتر نیست.
- `datagrams_forwarded` و `datagrams_returned`: تعداد دیتاگرام‌های نوشته‌شده در هر جهت، شامل بستهٔ صفر بایتی.
- `local_datagram_drops`: حذف بستهٔ شناخته‌شده در همین پردازش؛ معادل افت بستهٔ مسیر شبکه نیست.
- `probe_runs`: تعداد درخواست‌های سنجش واردشده به سرویس سنجش سرور؛ لزوماً همگی موفق نیستند.
- در udp-edge شمار active مربوط به نشست‌های مبدأ UDP است؛ در سرور، اتصال‌های سنجش هم موقتاً ظرفیت اشغال می‌کنند.

این شمارنده‌ها سربار TLS را حساب نمی‌کنند و به‌تنهایی تحویل داده به برنامهٔ مقصد را اثبات نمی‌کنند.
با راه‌اندازی مجدد صفر می‌شوند. مقادیر دو سرور را با هم جمع نکن؛ ممکن است همان داده را دوبار بشماری.
`/healthz` فقط زنده‌بودن API را نشان می‌دهد؛ آزمون انتهابه‌انتهای مقصد نیست.
این نسخه نرخ لحظه‌ای پهنای باند را نمایش نمی‌دهد.

در طراحی نهایی، رابط‌های ترمینال و وب به یک API مدیریتی مشترک متصل می‌شوند.
فعلاً CLI فایل را می‌خواند و صفحهٔ وب از API فقط وضعیت را می‌گیرد؛ مدیریت کامل وب هنوز ساخته نشده است.

هر مرحله باید روی مسیر یکسان با ابزارهای مرجع و یک خط مبنای بدون تونل مقایسه شود:
سرعت دادهٔ مفید دریافتی، تأخیر زیر بار، اتصال هم‌زمان، CPU، حافظه و زمان بازیابی.
آزمایش محلی یا موفقیت تست‌ها، اثبات امنیت کامل یا آمادگی استفادهٔ عمومی نیست.

## ساختار کد

- `main.go`: فرمان‌ها و چرخهٔ اجرای پردازش.

- `selftest.go`: تست داخلی انتقال و سنجش روی لوپ‌بک.
- `scripts/install.sh`: نصب واقعی یا نصب در ریشهٔ آزمایشی بدون تغییر سیستم.
- `scripts/build-release.sh`: ساخت بسته‌های دو معماری و checksum.
- `config.go`: اعتبارسنجی تنظیمات و TLS.
- `engine.go`: انتقال داده، سقف اتصال و شمارنده‌ها.
- `reverse.go`: پروتکل کنترل معکوس، شناسهٔ یک‌بارمصرف و اتصال مجدد.
- `udp.go`: نشست‌های مستقل UDP، قاب‌بندی دیتاگرام و صف محدود.
- `probe.go`: اندازه‌گیری با محدودیت حجم و زمان، هش داده و رسید دریافت.
- `udp_probe_test.go`: مرز دیتاگرام، جداسازی کاربران، انقضای نشست و سنجش TLS.
- `pki.go`: ساخت هویت‌های آزمایشی یک جفت سرور.
- `admin.go` و `status.html`: API مشاهده و صفحهٔ فارسی وضعیت.
- `engine_test.go`: آزمون انتقال واقعی با mTLS و حالت‌های خطا.
- `reverse_test.go`: انتقال معکوس، بازیابی کنترل، هویت، ضربان و مصرف یک‌بارهٔ شناسه.

فایل `VALIDATION.md` نتیجهٔ آزمون همین بسته را ثبت می‌کند.


## UDP در نسخهٔ ۰٫۳

فایل‌های `udp-edge.json` و `udp-relay.json` با init تولید می‌شوند. در نمونهٔ محلی:
ورودی UDP برابر 8081، پورت TCP/TLS بین سرورها برابر 7445 و مقصد UDP برابر 9001 است.
برای تست خودکار فقط `python3 scripts/udp_smoke.py` کافی است.
برای اجرای دستی، سرویس UDP مقصد را روی 9001 اجرا کن و در دو ترمینال:

```bash
./bin/tunnellab-linux-amd64 run -config demo/udp-relay.json
./bin/tunnellab-linux-amd64 run -config demo/udp-edge.json
```

UDP معکوس هنوز ساخته نشده است. این حالت، UDP را داخل TCP/TLS حمل می‌کند؛ با افت بستهٔ
مسیر TCP، دیتاگرام‌های بعدی همان نشست می‌توانند پشت ارسال مجدد معطل شوند. برای بازی یا
ارتباط حساس به تأخیر هنوز نباید آن را جایگزین UDP بومی فرض کرد. در مرحلهٔ بعدیِ انتخاب
بستر، استفاده از QUIC/DTLS استاندارد با کتابخانهٔ معتبر بررسی می‌شود.

هر آدرس و پورت مبدأ، نشست مستقل با یک اتصال TLS جدا و یک سوکت UDP مقصد جدا دارد.
نشست بی‌فعالیت با idle_seconds منقضی می‌شود؛ شکست کانال داده آن نشست را پایان می‌دهد.
اولین بسته پس از قطع/انقضا ممکن است از دست برود. برنامهٔ مصرف‌کننده باید رفتار عادی UDP
و امکان گم‌شدن بسته را در نظر بگیرد. تغییر پورت مبدأ یک نشست تازه است، نه مهاجرت نشست.

بیشینهٔ دیتاگرام پذیرفته‌شده 65507 بایت است؛ بستهٔ صفر بایتی هم معتبر است.
سقف نشست‌ها max_connections است. صف هر نشست حداکثر udp_queue_packets بسته
(پیش‌فرض ۸، بازهٔ ۱ تا ۶۴) و مجموعاً 256 KiB محتوای بسته نگه می‌دارد؛ هرکدام زودتر پر شود
بستهٔ جدید حذف می‌شود. این سقف فقط محتوای صف است؛ حافظهٔ TLS، سوکت و بافرهای انتقال جداست.
برای نمونه، ۲۵۶ نشست می‌توانند تا ۶۴ MiB محتوای صف، به‌علاوهٔ سربارهای دیگر، نگه دارند.
آمار حذف بستهٔ محلی، مدرک اندازه‌گیری افت بسته در اینترنت نیست.

## سنجش ارتباط با probe

وقتی relay مستقیم، udp-relay یا reverse-edge اجراست، از فایل تنظیمات سمت متصل‌شونده استفاده کن:

```bash
./bin/tunnellab-linux-amd64 probe -config demo/edge.json -bytes 1048576 -rounds 8
./bin/tunnellab-linux-amd64 probe -config demo/udp-edge.json -bytes 1048576 -rounds 8
./bin/tunnellab-linux-amd64 probe -config demo/reverse-relay.json -bytes 1048576 -rounds 8
```

هر سه نمونه از کانال TCP/TLS استفاده می‌کنند؛ حتی نمونهٔ udp-edge افت بسته یا تأخیر UDP بومی
را نمی‌سنجد. ابزار تا سرور مقابل را آزمایش می‌کند، نه سرویس target یا کل مسیر کاربر نهایی.
برای بررسی صحت مقصد، آزمون انتقال جداگانه لازم است.

گزارش JSON شامل این موارد است:

- tcp_tls_setup_ms: زمان برقراری TCP و TLS و بررسی گواهی.
- application_rtt_min_ms / mean / max / stddev: رفت‌وبرگشت پیام در برنامه؛ شامل پردازش و صف‌بندی.
- download_goodput_mbps: دادهٔ دریافت‌شده و تأییدشده با SHA-256، تقسیم بر زمان مرحلهٔ دریافت.
- upload_confirmed_goodput_mbps: دادهٔ ارسال‌شده، با رسید تعداد بایت و هش از گیرنده.
- packet_loss_measured: همیشه false؛ TCP ارسال مجدد را از این آزمون پنهان می‌کند.

این سنجش یک جریان دارد؛ مراحل دانلود و آپلود پشت سر هم‌اند. زمان دریافت شامل درخواست آغاز
دانلود و بررسی هش، و زمان آپلود شامل دریافت رسید است؛ اعداد، ظرفیت خام لینک نیستند.
اندازهٔ آزمون روی نتیجه اثر دارد و سنجش روی لوپ‌بک، معیار سرعت اینترنت نیست.
هر آزمون ۱ تا ۳۲ نمونهٔ RTT و 1024 تا 16777216 بایت در هر جهت دارد؛ سرویس آزمون پس از
۳۰ ثانیه پایان می‌یابد. همان احراز هویت دوطرفه و سقف اتصال listener اعمال می‌شود.
آزمون ممکن است روی ترافیک زنده اثر بگذارد؛ خودکار از صفحهٔ وضعیت اجرا نمی‌شود.
